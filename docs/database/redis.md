# Redis Data Design

This document covers every Redis key used by the system, both Lua scripts, and the Pub/Sub channel. All key patterns are generated by `src/utils/redisKeys.js` — use that module everywhere to avoid typos and key collisions.

---

## Key Schema

| Key Pattern | Redis Type | TTL | Purpose |
|---|---|---|---|
| `inventory:product-{id}` | String (integer) | None | Live available inventory counter; decremented atomically on reserve, incremented on expiry/cancel |
| `cart:user-{userId}` | Set | None | User's active cart; members are cart entry strings |
| `{productId}:rev-{uuid}` | Set member value | — | Cart entry format stored inside the cart set |
| `reservation:product:{id}:user-{userId}:rev-{uuid}` | String | 600 s | Proves a reservation is still live; `validate_cart.lua` checks existence |
| `cleanup-lock` | String | 300 s | Distributed mutex for `cleanupWorker`; prevents concurrent cleanup runs |

---

## Key Details

### `inventory:product-{id}`

**Type**: String (Redis stores it as a plain integer string).

**TTL**: None — this key is permanent for the lifetime of the product.

**Who writes it**:
- `sync-inventory.js` sets all inventory keys on API server startup.
- `decrement_inventory.lua` decrements it atomically on a successful reservation.
- `inventory.service.js` → `returnStock()` increments it when a reservation expires, a job is cancelled, or an admin cancels an order.

**What happens when it is missing**: If the key does not exist, `INCR` creates it at `0` and then increments to `1`. `decrement_inventory.lua` treats a missing key as "out of stock" (returns `-1`) because `GET` on a missing key returns `nil`, which the script guards against.

---

### `cart:user-{userId}`

**Type**: Redis Set. Each member is a cart entry string in the format `{productId}:rev-{uuid}`.

**TTL**: None — the cart persists until explicitly cleared.

**Who writes it**:
- `SADD` in `routes/products.js` (reserve) adds an entry.
- `SREM` in `routes/webhook.js` and `workers/processors/expiryProcessor.js` removes entries on fulfillment or expiry.

**What it enables**: The checkout page reads the cart set to display items and pass them to `validate_cart.lua`. The expiry worker removes the entry from the cart when it expires an order.

---

### `reservation:product:{id}:user-{userId}:rev-{uuid}`

**Type**: String (value is not semantically important — existence is the signal).

**TTL**: 600 seconds (10 minutes).

**Who writes it**: `SETEX` in `routes/products.js` immediately after a successful reservation.

**What happens when it expires**: The key silently disappears from Redis. The next time `validate_cart.lua` runs, it checks `EXISTS` on this key — if it returns `0`, the item is added to `expiredItems` and checkout is rejected for that item.

**What happens when the `expiresWorker` catches the expiry**: The worker checks `expires_at < NOW()` in PostgreSQL (not the Redis TTL). The two mechanisms are independent — the Redis TTL prevents checkout of an expired reservation, and the PostgreSQL `expires_at` allows the worker to identify and clean up the database row even if Redis has already forgotten the key.

---

### `cleanup-lock`

**Type**: String.

**TTL**: 300 seconds.

**Who writes it**: `cleanupWorker` attempts `SET cleanup-lock running NX EX 300` at the start of each cron tick.

**What `NX` means**: The key is only written if it does not already exist. This is atomic — exactly one caller wins per tick.

**What happens when the process crashes mid-cleanup**: The 300-second TTL ensures the lock automatically expires, allowing the next cron tick to acquire it without manual intervention.

## Lua Scripts

Both scripts are evaluated with `redis.call("EVAL", script, numkeys, ...keys)`. They run atomically inside Redis's single-threaded executor.

### `decrement_inventory.lua` — Atomic Reserve

**Location**: `decrement_inventory.lua` (project root).

**Called by**: `routes/products.js` — `POST /product/:id/reserve`.

**Keys**: `inventory:product-{id}`.

**Purpose**: Read the current inventory count and decrement it atomically if stock is available. Prevents two concurrent requests from both seeing "1 available" and both decrementing to 0.

**Logic** (pseudocode):
```lua
-- KEYS[1] = inventory:product-{id}
local current = redis.call("GET", KEYS[1])
if current == nil or tonumber(current) <= 0 then
  return -1   -- out of stock signal
end
return redis.call("DECR", KEYS[1])  -- returns new value
```

**Return values**:
- `>= 0` — reservation succeeded; value is the new inventory count after decrement.
- `-1` — out of stock; request should return `409`.

---

### `validate_cart.lua` — Atomic Checkout Validation

**Location**: `validate_cart.lua` (project root).

**Called by**: `routes/products.js` — `POST /product/create-payment-intent`.

**Keys**: `cart:user-{userId}` + reservation keys for each cart item.

**Purpose**: In one atomic operation, read the user's cart, check whether every reservation TTL key still exists, and split items into `validItems` (TTL key present) and `expiredItems` (TTL key gone). Prevents a user from checking out with an expired reservation.

**Logic** (pseudocode):
```lua
-- KEYS[1] = cart:user-{userId}
local members = redis.call("SMEMBERS", KEYS[1])
local valid = {}
local expired = {}

for _, entry in ipairs(members) do
  -- entry format: "{productId}:rev-{uuid}"
  local productId = string.match(entry, "^(%d+):")
  local uuid      = string.match(entry, ":rev%-(.+)$")
  local reservationKey = "reservation:product:" .. productId
                       .. ":user-" .. ARGV[1]   -- userId passed as ARGV
                       .. ":rev-" .. uuid

  if redis.call("EXISTS", reservationKey) == 1 then
    table.insert(valid, entry)
  else
    table.insert(expired, entry)
  end
end

return { valid, expired }
```

**Return value**: A two-element array `[validItems[], expiredItems[]]`.

## Pub/Sub Channel

### `inventory-updates`

| Field | Value |
|---|---|
| Channel | `inventory-updates` |
| Message encoding | JSON string |
| Publishers | `inventory.service.js` (`returnStock`), `routes/products.js` (reserve) |
| Subscriber | `src/sockets/index.js` |

**Message format**:
```json
{ "productId": "1", "newInventory": 4 }
```

Both fields are strings as emitted. The subscriber in `sockets/index.js` passes `newInventory` directly in the Socket.IO emit payload; the browser client receives it as a number (JSON parsing converts it).

**Publisher pattern** (`inventory.service.js`):
```js
const newCount = await redisClient.incr(`inventory:product-${productId}`);
await redisClient.publish("inventory-updates", JSON.stringify({
  productId: String(productId),
  newInventory: newCount,
}));
```

For the Socket.IO bridge that receives and forwards these messages, see [../api/websockets.md](../api/websockets.md).

## Key Expiry Behaviour Summary

| Key | Expires | Effect of Expiry |
|---|---|---|
| `reservation:product:…` | 600 s | `validate_cart.lua` treats the item as expired at checkout; `expiresWorker` independently catches it via `expires_at` in PostgreSQL |
| `cleanup-lock` | 300 s | Lock automatically released; next `cleanupWorker` cron tick can acquire it |
| `inventory:product-{id}` | Never | Must be explicitly deleted or overwritten; `syncInventoryToRedis` resets it on startup |
| `cart:user-{userId}` | Never | Accumulates until entries are removed by `SREM` on fulfillment or expiry |
